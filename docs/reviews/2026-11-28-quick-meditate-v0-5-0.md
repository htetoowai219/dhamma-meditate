# Code Review: Phase 09 — Quick Meditate & v0.5.0 Release Prep (`2026-11-28`)

- **Project Mode:** Prototype / MVP
- **Scope:** 18 files (uncommitted working-tree changes on `main`)
- **Reviewer:** Read-only `research` subagent (`pro` model)
- **Verdict:** Changes requested → **Resolved & Re-Verified (`PASS`)**

## Summary
Phase 09 implements Quick Meditate cleanly on the happy path—reusing the Session Editor cards and `MeditationPlaybackService` two-zone engine with zero Room `sessions` writes, solid `QuickMeditateDraft` unit tests, and 1:1 EN/MY string parity (`217` keys each). However, there are **two Major state-desynchronization bugs** in normal single-window navigation flows: `QuickMeditateViewModel` caches stale deleted tracks and transient error inputs across navigations (causing wrong-track removal and wrong timer calculations), and `SessionPlayerViewModel` loses access to active playback controls if the user taps **Reset** in Setup while Quick Meditate is playing. Both fixes are small and localized.

## Major

### 🟠 `QuickMeditateViewModel` caches stale `draftState` after Library track deletion and across navigations — `app/src/main/java/com/dhammameditate/ui/quickmeditate/QuickMeditateViewModel.kt:75-177`
- **Problem:** `QuickMeditateViewModel` is scoped to `MainActivity` with a fixed key (`key = "quick_meditate_setup"` at `MainActivity.kt:443`), so `init` runs only once per Activity lifetime and calls `trackRepository.observeTracks().first()` once. When a track in the draft is deleted from the Library, `uiState` filters it out in the derived `combine`, but `draftState` and `QuickMeditateStore` remain stale. All mutations (`addTrack`, `moveTrackUp`, `moveTrackDown`, `removeTrack`, `selectPresetMinutes`, `selectFullMainQueue`, `onCustomMinutesChanged`) index and compute against `draftState`, and transient invalid `customMinutesInput`/`capNotice` survive leaving and re-entering Setup.
- **Impact:** Selecting `[T1, T2]`, going to Library to delete `T1`, and returning to Quick Meditate displays `[T2]` at index `0`—tapping **Remove (`X`)** on `T2` calls `removeTrack(MAIN, 0)` and deletes the hidden `T1` while `T2` stays on screen; tapping **Full** or adding a track uses `T1 + T2` duration and re-persists deleted `T1` into `QuickMeditateStore`. Also violates spec Section 12.3 step 5 (`dhammameditate-shared-spec.md:562`).
- **Suggested Fix:** Continuously collect `trackRepository.observeTracks()` in `QuickMeditateViewModel.init`, reconciling `draftState` on every emission (pruning deleted tracks, refreshing `TrackEntity` metadata, clamping `targetDurationMs` via `TimerValidation.reconcileTimerAfterMainChange` with cap notice, and persisting reconciled changes to `QuickMeditateStore`). Mirror `SessionEditor` by adding `instanceId: Long` to `AppDestination.QuickMeditateSetup` in `MainActivity.kt` (and `AppDestinationSaver`) so re-entering Setup starts with clean transient input state while surviving rotation/process death.

### 🟠 Tapping `Reset` (or editing Setup) while Quick Meditate is playing locks the user out of active player controls — `app/src/main/java/com/dhammameditate/ui/sessionplayer/SessionPlayerViewModel.kt:71-108`
- **Problem:** Per AC-2 and spec Section 12.2 (`Reset isolation`), tapping **Reset** on `QuickMeditateSetup` clears `QuickMeditateStore` without stopping active playback. However, `SessionPlayerViewModel.sessionLoadFlow` constructs the ephemeral `SessionWithQueues` solely from `quickMeditateStore.draft`, so clearing the store emits `session = null` and causes `SessionPlayerScreen.kt:127-199` to render `"Quick Meditate not ready"` instead of the active player. Editing Setup tracks without starting also desynchronizes `ReadOnlyQueueOverviewCard` from the actively playing queue.
- **Impact:** Starting Quick Meditate → Back → Quick Meditate → **Reset** (audio keeps playing) → Back → tapping `ActiveSessionBanner` or the notification opens `"Quick Meditate not ready"` with no Pause, Skip to Main, Stop & Reset, or countdown controls while audio plays in the background.
- **Suggested Fix:** Add `activeIntroTrackIds: List<String> = emptyList()` and `activeMainTrackIds: List<String> = emptyList()` to `PlaybackSnapshot` (`PlaybackState.kt`), populated in `MeditationPlaybackService.publishSnapshot` from `activeQueueEntries`. In `SessionPlayerViewModel`, when `isQuickMeditate && playback.activeSessionId == sessionId && playback.isActive && playback.activeMainTrackIds.isNotEmpty()`, build the active `SessionWithQueues` from `playback.activeIntroTrackIds`, `playback.activeMainTrackIds`, and `playback.targetDurationMs` resolved against `trackRepository.observeTracks()`, falling back to `quickMeditateStore.draft` once `IDLE`/`COMPLETED`.
